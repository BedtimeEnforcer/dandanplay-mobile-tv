## 原审查发现（第 1–6 项已按上方记录修复）

### P1：投屏与接收可靠性

1. **电视端展示“投屏地址”，手机端却没有可用的手动输入入口。**电视首页在 `tv_component/.../TvMainActivity.kt:135-143` 显示 IP 和端口；手机端找不到接收端时，`storage_component/.../StorageFileActivity.kt:421-430` 只提供“知道了”。旧“新增投屏设备”流程虽有输入连接，但 `common_component/.../MediaTypeExt.kt` 已隐藏该入口，媒体库还会过滤旧投屏项。因此热点或组播受限时，电视显示的地址无法在当前手机端用于投屏。电视端的二维码也缺少与当前手机投屏流程对应的入口。
2. **电视端“启动时自动接收”开关无效。**设置页 `storage_component/.../ScreencastActivity.kt:62,124-125` 读写该开关，电视首页 `tv_component/.../TvMainActivity.kt:43-46,103-116` 每次创建都直接启动接收服务，不检查开关。首次启动时设置页默认显示关闭，但服务实际上已启动。
3. **接收状态可能显示“运行中”而端口没有监听。**`storage_component/.../ScreencastReceiveService.kt:81-83` 在 `onCreate` 就发出运行状态；`onStartCommand` 遇到空 Intent 或无端口时在 93-99 行直接返回，HTTP 服务尚未建立。启动失败时也会先短暂显示运行。电视首页只监听这个状态，无法区分“服务对象存在”和“可接收投屏”。
4. **快速切换视频时，设备选择可能投错文件。**`storage_component/.../StorageFileViewModel.kt:47,78-80` 只有一个全局 `pendingCastFile`；多设备选择后的 `castItem` 和带密码的接收端选择在 104-105、133-134 行重新读取它。用户在文件 A 的设备列表打开期间点了文件 B，最后选择 A 的设备会取到 B。重复发起 DLNA 搜索也没有统一取消与去重。

### P2：媒体正确性与兼容性

5. **字幕可能串集。**`common_component/.../SubtitleFinder.kt:67-82` 只判断字幕名是否以视频基础名开头。`第1集.mp4` 会把 `第10集.srt` 当成候选；应要求基础名后面是文件结束或 `.`、空格、下划线等明确分隔符，并覆盖语言后缀。
6. **部分 DLNA 设备会被发现却不能播放。**`storage_component/.../SsdpDiscovery.kt:232-235` 接受任意版本的 AVTransport 服务；`storage_component/.../DlnaController.kt:20,93,129` 固定用 `AVTransport:1` 发 SOAP。若设备只暴露 v2/v3，发现成功后控制请求可能被拒绝。需把发现到的完整服务类型传给控制器。
7. **电视端默认允许同局域网设备直接发起播放。**首次启动在 `tv_component/.../TvMainActivity.kt:87-100` 关闭接收确认，接收密码默认未设置。适合自用网络，但共用网络上可能被其他设备打断播放。建议首启明确提示并提供“仅已配对手机可投”选项，且密码开启后对失败原因给出清楚反馈。

## 界面与体验风险（需设备验证）

- 手机端视频行内“绑定”“投屏”“更多”按钮只有 **34/34/30dp** 宽（`common_component/.../item_storage_video.xml:99,111,123`），容易误触；标题仍为 14sp。建议扩大可点击区域，并用简短文字或长按提示说明图标。
- 电视首页在历史 1080p 截图中布局清楚，但进入文件列表、设置、绑定弹幕和设备选择后复用了手机布局。部分底部选择项使用 16sp 字号，尚未验证所有控件的遥控器焦点、返回键和软键盘行为。应逐页走查 720p/1080p、不同显示缩放和电视过扫描设置。
- 手机端 DLNA 投屏后，`DlnaController` 虽有暂停、拖动方法，但目前调用点只有播放与停止。手机界面没有明显的暂停、进度与断开控制，也无法直接确认电视是否已拉流。建议加入简洁的投屏控制页和“连接中/播放中/失败”状态。
- 电视首页的 IP 地址只在创建时读取一次（`TvMainActivity.kt:135-143`）；网络切换后可能显示旧地址或一直隐藏。需要跟随网络与服务监听状态刷新。
- 当前修复版通用 APK 分别约 84.2 MB（手机端）和 83.6 MB（电视端）。电视端构建时，旧阿里云反馈库产生大量 D8 警告，但构建成功。应先做 APK 内容分析，再决定是否移除已无入口的追番、磁链、反馈或扫码依赖；避免仅凭入口隐藏就删模块。

## 建议实施顺序

1. **先修核心链路。**把“手动输入 IP:端口”放进手机端的接收端搜索页和未找到设备弹窗；连接前做可达性、协议版本与密码验证。把每次投屏的文件、目标、方式和请求编号封装成不可变请求，重复点击时取消旧请求。电视端按自动接收开关启动，只有 HTTP 端口真正监听后才显示“运行中”，服务重建时从已保存设置恢复。
2. **再修媒体匹配与兼容性。**修正字幕边界匹配并用 `第1集/第10集`、语言后缀和同目录弹幕文件做针对性验证；DLNA 使用发现到的 AVTransport 服务类型。区分“接收端已接受请求”和“电视已开始拉流”，失败时及时停止供流并显示原因。
3. **优化双端操作。**手机端扩大行内按钮触控面积，提供投屏中控制与明确状态；电视端逐页补齐焦点样式、方向键顺序、返回键和网络地址刷新。首页名称较长，应在实际电视启动器上核对是否被截断，并考虑首页显示短名、桌面保留全名。
4. **按场景验收。**至少测试同一 Wi-Fi、手机热点、找不到设备时手动连接、密码正确/错误、两种投屏来回切换、重复点击、后台重启、视频与弹幕字幕同目录、SMB/FTP/WebDAV、电视遥控器全流程。用本项目假 DLNA/假发送端脚本补充协议回归，但最终以手机和电视真机结果为准。
5. **最后再瘦身。**分析 APK 中的大型原生库和已不可达模块，按依赖关系逐项移除并复编两端。体积优化不应排在投屏可靠性和真机验证之前。
